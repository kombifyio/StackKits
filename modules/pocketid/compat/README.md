No new publisher, repository, registry, account, credential or release trigger is introduced. Stable still requires the product's existing attended release authority.

The public image workflow adds two native platform jobs, sequentially, using its existing hosted-runner lane. The original server image job stays unchanged. Each derivative build produces native OCI output with maximum BuildKit provenance and SBOM. The reused verified OCI layout adapter loads the same config and layer bytes for runtime qualification. `skopeo` is the native publisher prerequisite because it can copy that qualified OCI graph, including attestations, without rebuilding or converting its Registry digests. Missing `skopeo` fails before a source build; its version is read, and no installer or alternate publisher is used.

An unchanged amd64 embedded binary, license and runtime configuration reuse the hash-bound earlier 9/9 HTTP/PostgreSQL proof. A changed binary or a new architecture executes the retained real nine-case HTTP/PostgreSQL journey using synthetic users and owned temporary containers, with cleanup. The new arm64 platform is therefore pending until its actual native run succeeds. A source build or an image digest alone does not provide arm64 qualification.

Only qualified native OCI output can be copied to `pocketid-cas-<release-tag>-<architecture>-g<full-public-source-sha>`. A conflicting immutable tag is refused. The final index consists of both exact platform manifests and their provenance descriptors; its full-source tag is `pocketid-cas-<release-tag>-g<full-public-source-sha>`. It receives a native GitHub attestation from the same public workflow. This route does not update the server image's `latest` pointer.

## Module adoption and installed transition

The global module continues using the official upstream image. After publication, `adopt-pin.mjs` reads one exact successful original native run/attempt, both Registry platforms, and the signed index's exact source, tag and signer workflow. It emits a reviewable module patch into a new owned output directory. It edits neither the module nor a Node. Reconcile the emitted patch with current module source and regenerate affected catalog/module facts through the existing generator before publishing it. The image index and both platform qualifications must exist before this changes the all-platform module pin; amd64-only evidence cannot remove Pi/arm64 support.

The existing upstream watch must not substitute an official unfenced image after CAS-managed membership exists. Any later derivative update must retain the contract, migration and all-platform evidence. No ordinary rollback may bring an old binary back onto a managed database.

The installed transition is defined in `rollout-contract.json` and implemented for the existing single-host Core Docker/SQLite lifecycle by `internal/pocketidruntime`, the existing signed owner-runtime binding, and the native direct/OpenTofu/restored-root callers. The executor acts under the existing lifecycle mutation lock. It invalidates managed admission, rejects external/shared databases and duplicate volume consumers, disables the exact old container's restart, observes its stopped PID/exit, removes its restart identity without deleting the volume, then binds the selected new image/container/start/volume. The managed receiver re-observes that signed incarnation before its first provider effect. Ordinary official/manual initial lifecycle remains a no-op for this binding. A sticky managed binding refuses an unfenced downgrade. The unchanged provider patch and the existing nine-case PostgreSQL protocol evidence do not authorize an installed PostgreSQL transition. The integrated source and prior seven SQLite controls do not claim a complete native Core/OpenTofu/restore deployment or an actual owner-node rollout; those observations remain mandatory before activation.

Existing isolated protocol evidence proves the provider seam. Actual installed-node Photos/Files grant, revoke, restore, member-leave and active-session journeys remain required. No new landscape, direct provider provisioning, database replacement, data deletion or app removal is authorized by this recipe.
